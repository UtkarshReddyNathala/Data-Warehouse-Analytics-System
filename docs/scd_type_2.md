# Slowly Changing Dimensions (SCD)

Customer and product details change over time. A customer may move to a new country or get married. The warehouse handles these changes in two ways:

- **SCD Type 1** overwrites the old value. Only the latest information is kept.
- **SCD Type 2** keeps both. The old version is marked inactive (`is_current = 0`, with an `expiry_date`), and the new version is active (`is_current = 1`).

History is kept in the **Gold** layer, because that is where reports are built. Silver only holds the current, cleaned data.

## Customers: `gold.dim_customers` (Type 1 and Type 2)

| Column | Type | Why |
|---|---|---|
| `country` | 2 | Sales by country must stay in the country where the sale happened |
| `marital_status` | 2 | To keep the history of customer groups |
| `first_name`, `last_name`, `gender`, `birthdate`, `create_date`, `customer_number` | 1 | Changes here are corrections, so history is not useful |

Columns that track the versions:

| Column | Meaning |
|---|---|
| `effective_date` | When this version starts (this moment is included) |
| `expiry_date` | When this version ends (this moment is not included). Empty (NULL) means it is still valid |
| `is_current` | 1 = this is the current version |
| `is_deleted` | 1 = the customer was deleted in the source |

**How the customer table is loaded** (`gold.usp_load_dim_customers`, all in one transaction):

1. **Type 1 changes:** if `scd1_hash` changed, the new values are written to **every** version of that customer.
2. **Type 2 changes:** if `scd2_hash` changed, the current version is closed (`expiry_date = load time`, `is_current = 0`).
3. **Deletes:** if the customer is deleted in Silver, the current version is closed and `is_deleted = 1` is set.
4. **New versions:** every active customer without a current version gets a new row with a new **surrogate key** (an ID generated by the warehouse, separate from the source `customer_id`). The first version of a new customer is valid from `1900-01-01`, so all past sales link to it. Later versions start at the load time.

**Example:** a customer moves from Australia to France.

| customer_key | customer_id | country | effective_date | expiry_date | is_current |
|---|---|---|---|---|---|
| 1 | 11000 | Australia | 1900-01-01 | 2026-10-31 14:05 | 0 |
| 18490 | 11000 | France | 2026-10-31 14:05 | NULL | 1 |

## Rules that are always kept

| Rule | How it is enforced |
|---|---|
| Only one current version per customer | A filtered unique index (`UX_gold_dim_customers_current`) and a data quality rule |
| The end date comes after the start date | A CHECK constraint and a data quality rule |
| The current version has no end date | A CHECK constraint and a data quality rule |
| Versions never overlap | A data quality rule (CRITICAL) |
| A new version starts exactly when the old one ends | The same load time (`@load_ts`) is used for both dates |
| Surrogate keys are never reused | `IDENTITY` |

## Linking sales to the right customer version

`gold.usp_load_fact_sales` links each sale to the customer version that was valid **on the order date**. This is a **point-in-time lookup**:

```sql
WHERE d.customer_id = c.sls_cust_id
  AND d.effective_date <= c.sls_order_dt
  AND (d.expiry_date IS NULL OR d.expiry_date > c.sls_order_dt)
```

If the order date is missing, the latest version is used. Sales that are already loaded are never moved to a newer version.

There are two ways to look at sales in reports:

- **"As it is"** (`gold.vw_fact_sales` + `gold.vw_dim_customers`): every sale shows the customer's **current** details.
- **"As it was"** (`gold.vw_fact_sales_history` + `gold.dim_customers`): every sale shows the customer's details **at the time of the sale**.

`scripts/analytics/18_historical_scd_analysis.sql` compares the two.

## Products: `gold.dim_products` (Type 1)

There is one row per product number, holding the current version from Silver. When a product's details change, the row is overwritten (changes are found by comparing hashes).

Products that no longer have a current version are kept, because sales still point to them, but they are marked `is_active = 0`.

The source data already has date ranges for each product version (`prd_start_dt`, and `prd_end_dt`, which Silver works out). These stay in `silver.crm_prd_info`, so product history can be added later if needed.
